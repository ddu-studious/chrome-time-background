## 1. 背景与问题分析

### 1.1 已发现的搜索缺陷

**核心 Bug**：相同语义的查询，因书写格式不同导致搜索结果截然不同。


| 查询输入                  | 结果         | 原因                                        |
| --------------------- | ---------- | ----------------------------------------- |
| `我要学习 Agent`（中英文间有空格） | ✅ 3 条关键词匹配 | 空格分词 → `["我要学习", "agent"]` → "agent" 匹配标题 |
| `我要学习Agent`（中英文间无空格）  | ❌ 未找到匹配    | 整体 → `["我要学习agent"]` → 作为子串匹配不到任何字段       |


### 1.2 根因分析

#### 关键词搜索层

当前分词策略（`query.split(/\s+/)`）仅按空格拆分，存在三个缺陷：

1. **中英文交界不分词**："我要学习Agent" 被当作一个 term
2. **无停用词过滤**："我"、"要" 等无语义的虚词参与匹配，浪费权重甚至产生噪音
3. **无子串扩展**：长中文词 "我要学习" 不会被拆解为 "学习" 等有意义的子词

#### 语义搜索层

1. **固定阈值过高**：余弦相似度阈值 `0.3` 对于中文自然语言查询和英文标题的跨语言匹配偏高
2. **Embedding 信息稀疏**：未抓取摘要的书签 embedding 仅含 `title + domain`，语义密度不足
3. **查询向量质量**："我要学习Agent" 中的虚词会稀释 embedding 中有用语义

### 1.3 用户需求

> "支持我输入一段话（需求）帮我找到我想要的内容、文档"

用户期望像跟人说话一样搜索，例如：

- "帮我找一个学习 Agent 的教程" → 能搜到 Agent 相关的教程类书签
- "我最近在看的前端框架" → 能搜到 React/Vue 等前端相关收藏
- "有没有关于 AI 编程的文章" → 能搜到 LLM、Copilot、AI coding 相关书签

## 2. 目标

在 v2.2.0 基础上，不引入外部服务，通过优化搜索管道实现：

1. **修复中英文混合分词 Bug**：任何格式的输入都能正确搜索
2. **智能查询预处理**：停用词过滤 + N-gram 子串扩展 + 中英文交界分词
3. **动态语义阈值**：根据查询特征自适应调整
4. **可选查询扩展**：利用已配置的 LLM 做查询意图理解（不增加新服务依赖）

### 核心决策


| 讨论项                  | 决策             | 理由                        |
| -------------------- | -------------- | ------------------------- |
| 是否需要外部分词服务           | **不需要**        | 正则分词 + N-gram 已能覆盖 90% 场景 |
| 是否引入 jieba-wasm      | **v2.4.0 再评估** | 23MB+ 体积对扩展过大，优先用轻量方案     |
| 是否引入 Transformers.js | **v2.4.0 计划**  | 可替代 API 调用，但需单独规划         |
| 查询扩展方式               | LLM 查询理解（可选）   | 复用已有 AI 配置，用户手动触发         |
| 语义阈值策略               | 动态阈值           | 根据查询长度和类型自适应              |

## 3. 技术方案

### 3.1 智能分词器（`_tokenize`）

替换原有 `query.split(/\s+/)` 为多层分词管道：

```
输入: "我要学习Agent的最佳实践"
  │
  ▼ Step 1: 中英文/数字交界插入空格
  "我要学习 Agent 的最佳实践"
  │
  ▼ Step 2: 标点符号归一化
  "我要学习 Agent 的最佳实践"
  │
  ▼ Step 3: 空格分词 + 小写化
  ["我要学习", "agent", "的最佳实践"]
  │
  ▼ Step 4: 停用词过滤（单字虚词）
  ["我要学习", "agent", "最佳实践"]  ("的" 被过滤)
  │
  ▼ Step 5: 中文 N-gram 扩展（2-3 字子词）
  ["我要学习", "agent", "最佳实践", "学习", "最佳", "佳实", "实践", "要学", "最佳实", "佳实践"]
  │
  ▼ Step 6: 去重 + 二次停用词过滤
  ["学习", "agent", "最佳实践", "最佳", "实践"]
```

#### 停用词表（中文常见虚词）

```
我、你、他、她、它、们、的、了、着、过、是、在、有、个、
要、想、去、到、把、被、让、和、与、或、但、而、就、都、
也、还、又、这、那、什么、怎么、如何、能、可以、会、不、
很、非常、太、最、更、一、一个、一些、所以、因为、如果、
帮我、找、搜索、查找、有没有
```

### 3.2 关键词搜索评分优化


| 变更        | 旧行为            | 新行为                                 |
| --------- | -------------- | ----------------------------------- |
| 分词        | `split(/\s+/)` | `_tokenize()` 多层管道                  |
| N-gram 匹配 | 无              | 2-3 字子词扩展匹配                         |
| 权重分配      | 固定权重           | 原始 term 权重 ×1.0，N-gram term 权重 ×0.5 |
| 惩罚        | 未命中 -5         | 按 term 重要性加权惩罚                      |


### 3.3 语义搜索优化

#### 动态阈值

```javascript
_getDynamicThreshold(query) {
    const len = query.length;
    if (len <= 5) return 0.35;     // 短查询（关键词）：要求较高精度
    if (len <= 15) return 0.25;    // 中等查询
    if (len <= 30) return 0.20;    // 长查询（需求描述）
    return 0.15;                   // 超长查询（自然语言）
}
```

**设计逻辑**：

- 短查询（如 "React"）精确度要求高 → 高阈值
- 长查询（如 "我想找一个学习Agent的教程"）包含噪音多，但语义丰富 → 低阈值

#### 查询向量优化

在调用 Embedding API 前，对查询文本做预处理（去停用词、提取核心语义词），使向量更聚焦：

```
原始: "我要学习Agent"
预处理: "学习 Agent"  ← 更聚焦的 embedding 输入
```

### 3.4 可选：LLM 查询扩展（手动触发）

当搜索结果不理想时，用户可选择 "AI 理解搜索" 功能：

```
用户输入: "帮我找一个关于如何开发 AI Agent 的教程或工具"
    │
    ▼ LLM 查询理解
{
    "intent": "学习AI Agent开发",
    "keywords": ["AI agent", "agent开发", "agent教程", "agent框架"],
    "expanded_queries": [
        "AI agent development tutorial",
        "agent framework tools",
        "agent-reach",
        "langchain agent"
    ]
}
    │
    ▼ 多查询融合搜索
    对每个 expanded_query 执行 hybridSearch → RRF 融合所有结果
```
