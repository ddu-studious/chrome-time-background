## 改动与复用边界

- Gateway 保留原 90 秒默认总限额，将首轮思考分配为三分之一，关闭思考恢复获得余下约 60 秒。其他场景仍走原单次预算；短自定义时限也按比例受限。
- 复用已有最多 100 条运行记录，仅在 conversationId / turnId、模型、原选择和策略版本相同，且前次计划已通过验证并成功恢复为 off 时，后续规划直接使用 off。继承来源记入 `recoveryFromRequestId`，原始 low/medium 等选择仍可审计。
- 同一轮沿用恢复后的规划从预算准备开始使用 off 的 1200 输出限额；实际调用最多使用原单次时限。没有重新执行业务动作。
- 用户确认/选择进入新执行轮，新需求、策略或模型变化、前次失败、服务重启或记录被淘汰，均不继承此临时状态。取消、每日配额和失败冷却沿用 admission 校验，不绕过保护。
- 时间线与完整历史显示恢复来源；没有改模型全局默认值或 LM Studio 加载配置。

此次直接复用本仓库 Gateway、admission、Provider 和 trace，不新增 SDK 或平行模型引擎。pi `@earendil-works/pi-coding-agent@0.85.1` 的公开压缩 API 和依赖锁文件保持原实现。LM Studio 原生 [Chat API](https://lmstudio.ai/docs/developer/rest/chat) 提供 reasoning 参数；[Streaming events](https://lmstudio.ai/docs/developer/rest/streaming-events) 支持流式进度，但此次修复不引入额外流解析器。底层日志虽然提示 off 不是某个 effort 字段的枚举，第一轮恢复的实际 reasoning_output_tokens 为 0，不能仅凭该警告断言关闭思考无效。
