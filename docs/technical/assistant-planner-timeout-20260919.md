# AI 工作台规划超时修复

## 当次证据

需求：清空队列，找到法老的热门歌曲，加入队列，随机播放。

生产历史调用 `19354d89e4e68a85c0fd55ecd6f5c86c` 和 `efe4b5bee8e20c1ec92a66cec58c1864`，与 LM Studio 的 `2026-09-19.1.log` 15:11–15:14 记录对应：

| 阶段 | 本项目请求 | LM Studio 实际结果 |
|---|---|---|
| 第一轮思考 | low，60 秒 | 输入 2089 tokens，首 token 约 11 秒；中断时 1000 输出、998 思考，无正式消息 |
| 第一轮恢复 | off，剩余约 30 秒 | 约 15 秒成功；输入 2070、输出 40、思考 0；返回读取队列状态计划 |
| 第二轮思考 | 再次 low，60 秒 | 输入 2371 tokens，首 token 约 16.7 秒；中断时 278 输出、277 思考，无正式消息 |
| 第二轮恢复 | off，剩余约 30 秒 | 约 27 秒时输入处理才到 87.1%，超时断开时约 98%，尚无输出 |

因此直接原因是**思考耗时过长、恢复时限不足，以及下一规划步骤重新开启了已经降级的思考**。第一轮与第二轮生成速率分别约 20.2 和 6.2 tokens/s，只能证明当时速度有波动，不能据此确定系统负载或内存方面的原因。

这次没有执行 `assistant.compact`，summary 为空、canCompact=false，输入估算 6260 远低于 28160 预算，没有输入超限错误。`compacted:false` 本身表示程序字段精简未触发；结合场景与检查点才能确认没有 pi 摘要调用。同一输入仅去掉 context envelope 的静态对照为 5769，新增保护上下文带来约 491 个保守估算 tokens，但并未触发长历史压缩或造成容量溢出。模型端实际输入为 2371，不能将保守估算当作真实 usage。

原 Provider 使用非流式请求，取消前未收到完整 JSON，因而本项目没有拿到 usage；日志里的统计是服务器在客户端断开后记下的。历史界面继续明确“服务未返回 token 用量”，不以估算或事后日志填成实时用量。

## 改动与复用边界

- Gateway 保留原 90 秒默认总限额，将首轮思考分配为三分之一，关闭思考恢复获得余下约 60 秒。其他场景仍走原单次预算；短自定义时限也按比例受限。
- 复用已有最多 100 条运行记录，仅在 conversationId / turnId、模型、原选择和策略版本相同，且前次计划已通过验证并成功恢复为 off 时，后续规划直接使用 off。继承来源记入 `recoveryFromRequestId`，原始 low/medium 等选择仍可审计。
- 同一轮沿用恢复后的规划从预算准备开始使用 off 的 1200 输出限额；实际调用最多使用原单次时限。没有重新执行业务动作。
- 用户确认/选择进入新执行轮，新需求、策略或模型变化、前次失败、服务重启或记录被淘汰，均不继承此临时状态。取消、每日配额和失败冷却沿用 admission 校验，不绕过保护。
- 时间线与完整历史显示恢复来源；没有改模型全局默认值或 LM Studio 加载配置。

此次直接复用本仓库 Gateway、admission、Provider 和 trace，不新增 SDK 或平行模型引擎。pi `@earendil-works/pi-coding-agent@0.85.1` 的公开压缩 API 和依赖锁文件保持原实现。LM Studio 原生 [Chat API](https://lmstudio.ai/docs/developer/rest/chat) 提供 reasoning 参数；[Streaming events](https://lmstudio.ai/docs/developer/rest/streaming-events) 支持流式进度，但此次修复不引入额外流解析器。底层日志虽然提示 off 不是某个 effort 字段的枚举，第一轮恢复的实际 reasoning_output_tokens 为 0，不能仅凭该警告断言关闭思考无效。
