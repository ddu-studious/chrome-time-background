# AI 工作台只读代码计算（`compute.run`）

日期：2026-10-12

## 结论

- **已实现 A 档：模型可以写一小段 JavaScript，对本任务已经取得的回执数据做统计、筛选、排序、去重、日期或数值运算。** 代码只在本机服务里、每次一个独立子进程内运行，没有网络、文件、子进程和任何业务对象，只返回 JSON。
- **默认关闭。** AI 设置里的“代码计算”开关（`computeEnabled`）默认 `false`，还要求总开关打开、场景 `assistant.compute` 未被禁用、沙箱依赖可用。任一不满足时，规划提示词和工具目录里完全没有 `compute.run`，行为与未实现前一致。
- **只做 A 档。** B 档（代码直接调用业务工具）和 C 档（持久化模型写出的工具）仍然禁止，原因见 `docs/research/research-assistant-dynamic-tools-20261012.md`；pi 0.85.1 没有内置沙箱，其自写扩展与进程同权限，不采用。
- 前提：用户确认**扩展不会上架 Chrome Web Store**，并接受只读计算每个任务多约 1–2 分钟。若以后改为上架，须重新评估（代码虽只在本机服务执行、扩展包内没有解释器，但审核口径未验证）。
- 同一轮还修了几处**共享的规划路径**（数组包装、Todo 复述、`alarm.list` 选择卡、提醒统计类提问的快捷路径、动作词误判、“没有可执行步骤”的提示文案），见“对共享路径的改动”；它们对默认关闭的用户也生效，需要一并 review。
- 真实本机模型（Qwen3.8-27B，替身队列/提醒，小样本）：关闭计算时 13 个分析类用例 0/13；开启后修复轮 16/16（样本内），修复完成后新写的 5 个留出样本 4/5（失败的一个暴露了“先算后做”的占位参数缺陷，已修）。计算类任务总耗时中位约 85 秒、最长 166 秒，5/16 超过 2 分钟。详见“真实本机模型评测”。

- 版本固定在 `local-ai/package.json`，锁文件已提交（含 `integrity`）。没有复制 SDK 源码，没有引用未导出的内部文件。
- **自有职责**：每次一个子进程与并发上限、墙钟强杀、取消、输出上限、封闭错误类、请求/输出校验；Gateway 的开关、预算、冷却、熔断与记录；扩展侧 Contract 登记、Todo 验收规则、Engine 回执语义、来源引用取回、时间线展示。上游只负责“在 WASM 里执行一段 JS”。
- **没有采用 pi**：已核对 pi 0.85.1 的安全文档，其扩展机制与进程同权限，没有沙箱；本项目对它的使用仍限于摘要、序列化与工具调用拦截三个库级能力。
- **没有采用 `isolated-vm`**：需要原生模块编译，且与 Node 版本强绑定；QuickJS-WASM 没有宿主对象，边界更小。

### `setMemoryLimit` 可被绕过（实测）

`runtime.setMemoryLimit()` 在这个 WASM 构建里**不统计 `realloc` 增长出来的块**：一个不断增长的数组/字符串可以越过它。因此不能把它当作唯一的内存保护。运行器改为给 QuickJS 一块有上限的 `WebAssembly.Memory`（初始 256 页、最大 1024 页 = 64 MiB），超出时引擎中止，运行器据此判为 `COMPUTE_MEMORY_LIMIT`。`setMemoryLimit(16 MiB)` 仍保留，用来更早拦住普通分配。

## 数据路径

1. 规划：Gateway 在 `assistant.plan` 场景把 `computeEnabled` 传给 `local-ai/assistant-service.mjs`。启用时，清单分析的完成条件目录和执行阶段的工具目录才出现 `compute.run`，并附一段用法（输入形状、分页读取、`input.refs["context:N"]` 就是回执的 observation 对象、返回约束、出错处理）。音乐应用里当前待办为 `compute.run` 时，执行阶段还会直接曝光 `music.queue` 工具组说明（只是合同，不授权也不执行；写入工具仍受 Todo 顺序与确认卡约束）：此前每个队列分析任务都以 `music.queue.list` 被拒为“尚未加载”开头，再走一轮 `tools.load`，白白多花一次模型调用和一个恢复名额。仅在开关开启、非清单分析、当前待办为 `compute.run` 且只选了音乐应用时生效，默认关闭时行为不变。
2. 校验：扩展与服务共用 `AssistantContract`。`compute.run` 登记为只读、所有应用可用，字段 `purpose`、`code`、`inputRefs`（可选）；`code` 原样保留不修剪；`inputRefs` 一旦提供就必须是 1 至 6 个互不重复的 `context:N`；**空数组等同没有来源，校验后直接去掉**（真实模型做纯日期/数值计算时常写 `"inputRefs":[]`，此前被拒绝而让任务停在无害的写法差异上；沙箱得到的数据不变）。`purpose`、`code`、`inputRefs` 都必须写在 `args` 里；写在步骤同级时，错误信息会点名该参数并说明属于 `args`。
3. 取数：`AssistantTools.computeRun` 用 `Context.sources` 取回**本任务已有回执**的独立副本（已净化凭证字段）；模型不能自己塞数据。输入为 `{ now, today, utcOffsetMinutes, refs }`，合计 ≤40 KB。引用已失效返回可恢复的 `CONTEXT_REF_EXPIRED`。
4. 执行：扩展通过内部动作 `ai_compute_submit`（只允许 `code` 与 `input`，限额与沙箱一致）请求 Gateway 的 `assistant.compute`；Gateway 计入总开关、场景开关、每日额度、冷却/熔断与取消，再交给 `ComputeProvider`。
5. 回执：返回 `{ output, outputBytes, elapsedMs, codeHash, inputDigest, engine }`。运行记录**只保存指纹**（代码哈希、输入摘要、输出字节数、耗时、错误类），不保存代码、输入或输出正文；用户开启历史正文留存时才按原规则保存。
6. 展示：时间线显示目的、可折叠的代码与输出。

## 沙箱边界

- 子进程：`node --permission`，只读权限限于运行器和三个固定依赖目录（真实路径，不含符号链接）；无写、子进程、Worker、网络、原生插件、WASI、调试器；环境变量为空；`--disallow-code-generation-from-strings`；每次一个，同时最多 2 个。
- 客体：QuickJS 里没有 `process`、`require`、`fetch`、`import()`、定时器或宿主对象；`console` 被替换为空操作；`Function` 构造器只能创建客体内函数。
- 限额：见对照表；超时由客体中断处理器和父进程强杀双重保证；父进程在子进程退出后才结算，被取消或完成的调用不留下子进程。
- 错误类：客体问题（`COMPUTE_SYNTAX_ERROR`、`RUNTIME_ERROR`、`TIMEOUT`、`MEMORY_LIMIT`、`STACK_LIMIT`、`OUTPUT_INVALID`、`OUTPUT_TOO_LARGE`，HTTP 422）是这次尝试的普通结果，进入 Engine 现有有界恢复，不触发熔断；基础设施问题（`COMPUTE_BUSY` 429、`COMPUTE_ISOLATION_UNAVAILABLE` 503、`COMPUTE_SANDBOX_FAILED`）和 Gateway 的 `COMPUTE_DISABLED`（403）、`COMPUTE_UNCONFIGURED`（503）会转成 `ASSISTANT_USER_INPUT_REQUIRED`，明确提示用户处理。
- 隔离不可用（缺依赖、Node 不支持 `--permission`）时拒绝执行并说明原因，**没有任何进程内 fallback**。
- Node 权限模型只是第二道防线，不是主边界；QuickJS 本身**没有经过独立审计**。

## Todo 与 Engine 语义

- `compute.run` 是只读工具：成功回执只是 observation，**不能证明任何业务动作已完成**。
- Todo 中它可以作为纯分析目标的验收条件（`args` 必须为空，代码与引用只在执行阶段给出）。原文含动作词（加入、删除、清空、播放、关闭……）时，不能只靠 `compute.run` 验收，必须另设动作目标；“先算后做”（分析目标列在动作目标之前）允许。
- 当前事项是写入工具时，仍可先做只读计算；其他越序工具照旧被拒绝。
- 只有成功回执才勾选；失败保持进行中并交给有界恢复。相同代码 + 相同输入指纹计入 `readSeen`，原样重复会被无进展保护拦住。
- 纳入 12 轮 / 12 工具 / 5 分钟与 3 次恢复的现有预算，不新增、不重置；取消会终止子进程，晚到结果不得更新任务。
- 动作类 Todo 的正确形态：`compute.run` 求出“歌最多的歌手”，再由 `music.queue.removeArtist` 展示确认卡（沙箱不执行任何写入）。
- **分析之后的动作目标不能预填自由文本参数。** Todo 一旦保存就不能改，验收参数必须与真实调用逐项相等；而“要删的歌手”是计算的结果，清单阶段不可能知道。同一原文分项里排在 `compute.run` 之后的目标，若带有不在原文里的自由文本参数（模型会写“执行阶段由分析结果确定”这类占位文字，或直接猜一个名字），`Todo.install` 以 `todo-arguments` 拒绝，信息点名条目、工具和参数名（不回显值），并要求 `args` 写成空对象；枚举、布尔、数字不受影响，原文里写明的值也保留（那是用户给的）。动作本身仍由它自己的回执验收。这条规则来自留出样本评测（见下），只在 Todo 含 `compute.run` 时才可能触发。

## 对共享路径的改动

这些改动由真实本机模型评测暴露的问题驱动，且都先写了失败测试。它们不只影响代码计算：

1. **规划输出信封修复**（`local-ai/assistant-service.mjs` 的 `unwrapPlanArray`，仅执行阶段）：本机模型常把整个计划或步骤列表包成 JSON 数组。只修外层信封，内部不改写：`[{"steps":…}]` 取出对象；全是 `tool` 的数组当作 `steps`；全是带 `text`/`source` 的行视为“复述待办清单”，交给既有 `todoTips` 检查——与真实清单完全相同则丢弃并要求给出下一步，有任何改动仍按“不能覆盖 Todo”拒绝。每个步骤仍走同一套工具、参数、范围、步数校验，Todo“每轮一个工具”规则不变。清单分析阶段不受影响。
2. **更可执行的合同错误信息**（`js/assistant-contract.js`）：数组、多余顶层字段、步骤带额外字段（提示不能带 `id`、`text`、`status` 并给出正确写法）、没有可执行步骤（原来误报“一次最多执行三个步骤”）。**不回显模型自写的键名**，只有两个例外可以点名：`todoId`，以及恰好是该步骤所选工具登记参数的键（例如 `inputRefs` 写在了 `args` 旁边：“inputRefs 是 compute.run 的参数，必须写在 args 里面”）。后者来自评测：两个提醒类用例的模型都把 `inputRefs` 写在步骤同级，原信息只列了 `id/text/status`，模型原样重复而停止。其他工具的参数、模型自造的键仍只给固定文案。仓库原有的 `test/assistant-plan-format.test.mjs` 断言“不能带其他字段”这个固定短语且不得回显自造字段名；信息措辞一度改得与它冲突，现已保留该短语，该文件未改动、全部通过。
3. **`alarm.list` 只读分析不弹选择卡**（`js/assistant-management.js`）：当前待办事项由 `compute.run` 验收时，只返回数据；管理类任务（没有 Todo、其他工具、分析项已完成）仍等待选择。
4. **提醒/闹钟的统计类提问不走本地“新建提醒”快捷路径**（`Contract.localPlan` 的 `alarmQuestion`）：含“有没有/哪些/哪个/几个/多少/几天/最早/最晚/一共……”且不含“提醒我、设置、创建、叫我……”的提醒类问题返回 `null`，交给规划器。此前它们被 `alarm.prepare` 接走，要么报“快捷入口仅支持新建提醒和查看列表”，要么可能把“周六或周日响的”误读成新建重复提醒。创建、`查看提醒` 列表和显式选择“创建提醒”技能的行为不变。**对默认关闭的用户同样生效**：这类提问现在会走一次规划而不是立刻报错。
5. **动作词误判**（`js/assistant-todo.js` 的 `actionText`）：“关闭状态的闹钟”“开启的提醒”这类描述状态的用法不再被当作动作；“关闭这个闹钟”“开启周末的闹钟”等动词用法仍被拦住。只影响 `compute.run` 的动作检查。
6. **提示词**（仅启用计算时才出现，关闭时与原来逐字节相同）：分页读取说明与来源都要放进 `inputRefs`、`input.refs[...]` 的形状、每轮只返回一个步骤的正确写法示例（读取一页与计算各一例，不用评测原话）、读取工具回执已含答案时不用 `compute.run`、没有动作的提问也必须列为一项目标；`purpose/code/inputRefs` 都写在 `args` 里；每轮只返回下一步（读下一页就只返回读取这一页，不要把之后的计算或动作一起写出来，也不加 `_step`、`_purpose` 之类的注释字段——评测里模型在读完第一页后常把“读第二页、计算、删除”写成一个带注释字段的数组）；动作的对象要由数据算出来时（“最多的”“最长的”“最近的”那一个）不要追问用户，先列一项 `compute.run` 分析目标，再列对应的动作目标（评测中“删除歌最多的那位歌手”一次被模型当成需要先征求同意的问题，任务停在 `clarify`，用户其实无须回答任何东西）；动作目标的 `args` 写成 `{}`，不预先写由分析得出的值（留出样本里模型曾写占位文字，见下）。
7. 本机既有的“含最近/上次等历史词 + 哪个/哪些”的问句会被记忆回忆快捷路径（`memory.recall`）接走，这是原有行为，**没有改**。含此类措辞的提醒类问题不会走代码计算。
8. **“没有可执行步骤”的提示文案**（`Contract.validatePlan`）：`steps` 为空时原来说“一次最多执行三个步骤”，对空列表是错的，评测里模型照着错误提示重复同样的输出。现在说明没有可执行步骤、给出正确写法并提醒不要复述待办清单；步骤超过三个的提示不变。仓库里 `test/assistant-todo-protocol.test.mjs` 的一条已提交断言原先匹配旧文案，已改为匹配新文案（其余断言不变）；这是全量测试才暴露出来的，之前只跑了与本功能相关的文件。
9. **分析之后的动作目标不能预填自由文本参数**（`Todo.install`，仅当同一原文分项里已有 `compute.run` 时），见上节。清单分析提示词（仅启用计算时）同步要求动作目标的 `args` 写成 `{}`。

## 真实本机模型评测

**对象与方法。** 模型 `qwen/qwen3.8-27b`（LM Studio，本机单并发），`reasoning=low` 起步（清单分析固定从关闭思考起步，见 `assistant-speed-20260929.md`）。用真实 Engine/Tools/Contract/Todo、进程内 Gateway 和真实沙箱子进程；队列与提醒是确定性替身，所有业务写入都会抛错并被计数（出现任何一次写入尝试即判失败）。判分只看最终任务状态和用户看得到的答案是否正确（逐个歌手核对首数、提醒有没有漏列或误列、天数与星期是否正确、确认卡里的歌手与首数是否正确），不看过程。命令：`node local-ai/evaluate-compute.mjs [--runs=N] [--cases=…] [--compute=on|off] [--trace]`，报告写在 `local-ai/.local/evaluations/`（不入库）。

**先说清楚这些数字能说明什么。** 样本很小、本机模型输出不是确定的、耗时随 LM Studio 的提示缓存是否命中差别很大（同一任务热缓存 12–18 秒，冷缓存可达 3–5 分钟）；下面是方向性证据，不是通过率保证。用例分三类：**调试用例**（8 个计算类，驱动了本文“对共享路径的改动”里的修复，所以对它们的最终结果是样本内的）、**留出样本**（5 个，修复完成后才写，不用于调试）、**对照**（4 个不该用计算的用例）。

| 第 3 轮 | 4/8 | 4/4 | 提醒类两例把 `inputRefs` 写在步骤同级而提示没点名；`"inputRefs":[]` 被拒绝；两例“模型返回格式无效”（未能稳定复现，多半与一轮写出多个步骤有关）；“删除歌最多的歌手”被当成需要先征求同意的问题 |

### 留出样本（修复完成后新写的 5 个，各跑 1 次）

| 用例 | 结果 | 耗时（秒） | 恢复 |
|------|------|------------|------|
| 队列里歌手的歌曲数量，最多的和最少的相差几首 | 通过 | 103 | 0 |
| 歌最多的那位歌手占整个队列的百分之几 | 通过 | 134 | 0 |
| 提醒里最早的和最晚的相差多少天 | 通过 | 82 | 0 |
| 2026 年 12 月 25 日是星期几 | 通过 | 50 | 0 |
| 删除队列里歌**最少**的那位歌手的歌（停在确认卡） | **失败** | 304 | 2 |

留出样本 4/5。失败的那个暴露了一个真实缺陷：清单阶段模型给动作目标写了 `{"artist":"<占位文字>"}`。Todo 保存后不可改，真实调用（歌手 = 算出来的名字）永远匹配不上，任务在重复失败后停止，用了约 5 分钟。这正是“先算后做”的核心场景，所以修了两层：清单分析提示词要求动作目标的 `args` 写成 `{}`；`Todo.install` 对排在 `compute.run` 之后、含不在原文里的自由文本参数的动作目标直接拒绝并指明原因（见“Todo 与 Engine 语义”）。修复后该用例再跑 2 次都通过（90 / 103 秒，0 次恢复，清单里动作目标的 `args` 都是 `{}`），但它此后已不再独立；另外在 7 个旧用例上做了一轮回归，7/7 通过（含 3 个对照）。端到端的“被拒绝→回到分析阶段→修正→确认卡前停住、0 次业务写入”另有一条 Engine 流程测试覆盖，不依赖真实模型。

### 对照：关闭代码计算（`--compute=off`）

同样 13 个分析/留出用例，各 1 次，关闭代码计算，其余相同：**0/13 通过**，共 24.4 分钟。失败形态：

- 清单阶段就停了（纯日期/数值/星期题，没有任何读取工具可作验收）：3 例，十几秒结束，报“不能返回空清单”；
- 有读取工具可选，但没能拿出答案：8 例。有的读完队列后被 Todo 的“全部完成后不能追加原计划之外的动作”卡住，有的输出格式无效，有的 Todo 验收参数与实际调用对不上，有的弹出 `alarm.list` 选择卡；
- 删除歌最多/最少歌手：2 例，超时或步骤格式错误。

这说明的是：**对“要从回执数据里算出答案”的问题，固定工具流程在这个本机模型上基本走不通**，不是说模型不会数数。简单问题不受影响：对照用例“队列里有多少首歌”在开启计算时也直接由读取工具回答，没有使用计算。注意这里的“关闭计算”仍带着本次对共享规划路径的修复，不是未修改的旧提交；没有在旧提交上另跑一轮。

### 这些评测没有说明的事

- 没有真实 Chrome 扩展、真实播放队列、真实提醒或真实账号的结果；替身队列只有 25 首、提醒只有 4–8 条，真实数据更大时可能碰到 6 页/40 KB/12 工具的上限。
- 耗时只在这台机器的这个模型上测过；换模型、换量化或冷缓存结果会不同。“每个任务多 1–2 分钟”的接受度对 5 个最慢的用例（2–3 分钟）并不总成立。
- 每个用例最多 2 次，没有统计置信度；“最终轮 16/16”是样本内结果，留出样本 4/5（含 1 次失败，已修）才是更接近泛化的信号。

## 边界与已知限制

- **能算的上限由读取工具决定。** `music.queue.list` 每页最多 20 首且只有 `ref/title/artist`，`alarm.list` 每页最多 20 条；`inputRefs` ≤6、合计 ≤40 KB，因此一次计算最多覆盖约 120 首队列。工具数上限 12 也限制翻页次数。
- **额外耗时主要来自规划轮数**：每个计算任务通常是 `tools.load` → 读取若干页 → `compute.run` → 结束确认，本机模型每个规划调用 3–30 秒，常有 30 秒首轮超时后关思考恢复；计算任务在全部待办完成后，现有逻辑还会多规划一次 `{"done":true}`（约 15–30 秒，既有行为，没有改）。
- **5 分钟任务上限没有为计算任务放宽。** 评测里最慢的成功任务 166 秒，失败的留出样本用满约 304 秒（含两次 30 秒的模型响应超时）；热缓存时同类任务只要十几到几十秒。“放宽上限换更高成功率”是用户决定，没有擅自改动。
- **规划输出没有 JSON Schema 约束**：`provider.generateObject` 只是在指令里要求 JSON，数组、多余字段、复述待办清单、一轮多步都是本机模型的常见偏差；这次只在信封层和提示词层缓解，没有引入结构化输出（需要单独评估 LM Studio 能力与对思考模式的影响）。
- 同一规划轮里**两次相同类别的格式错误**仍会按既有恢复规则停止（指纹只含工具、错误码、阶段与 `planIssue`，不含消息，所以第二个没有登记 `planIssue` 的规划无效错误会按“同一操作重复失败”停止）；没有改动这条规则。给更多错误登记 `planIssue` 能提高成功率，但属于共享路径的改动，需要单独评审，这次没有做。
- 沙箱依赖缺失时只关闭这一个场景，不影响本机服务其余能力；`./local-ai/service.sh restart` 前，旧服务不认识 `assistant.compute`。
- 代码计算结果是模型写的代码算出来的，**不保证正确**：UI 展示目的与代码供核对，答案仍应结合回执判断。

## 运行与排障

1. 在 `local-ai/` 目录运行 `npm ci`（安装固定版本的 QuickJS）。
2. `./local-ai/service.sh restart`，重新加载扩展。
3. 在 AI 设置打开“代码计算”开关（默认关闭；需总开关打开，`assistant.compute` 场景未被禁用）。
4. 排障：AI 控制台状态里的 `compute` 段会给出是否已配置、依赖错误、引擎版本与限额，场景列表里 `assistant.compute` 的 `modelEnabled` 表示开关是否实际生效；“依赖不可用”请先 `npm ci`；“进程隔离不可用”请确认 Node 版本支持 `--permission`。
