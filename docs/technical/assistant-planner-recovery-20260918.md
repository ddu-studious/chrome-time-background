# 规划模型只有思考、没有 JSON 的恢复

## 问题与配置边界

`assistant.plan` 原先固定 `maxOutputTokens: 1200`，覆盖 Provider 在开启思考时的 4096 默认值。历史中的一次 medium 和两次 low 调用均返回总输出 1199、思考 1199，没有正式计划。解析器把这种情况混在“未返回单一 JSON”错误中。

LM Studio 的上下文容量、单次生成上限和并发是不同参数。界面保存的加载配置不必等于已加载实例配置；以 `/api/v1/models` 的 `loaded_instances[].config` 核对运行实例。扩展仍串行调用本地模型，不跟随 LM Studio 并发配置放大请求数。

## 实现

- 规划关闭思考时申请 1200 tokens，开启时申请 4096；始终服从全局更小的预算。
- 已加载模型不再发送 `context_length: 8192`，复用模型运行实例配置。冷加载默认 12288，给规划最多约 6200 的输入估算与 4096 输出留空间；没有修改 LM Studio 的持久化设置。
- 区分 `MODEL_REASONING_BUDGET_EXHAUSTED`、`MODEL_NO_FINAL_OUTPUT`、`MODEL_RESPONSE_TIMEOUT` 和一般格式错误。不提取或执行思考文本里的 JSON。
- 仅 `assistant.plan` 且开启思考时，对上述三种失败允许一次关闭思考重试；普通格式错误、连接错误、业务合同失败不自动重试。
- 两次尝试共享控制面超时（默认 90 秒）。2026-09-19 根据真实输入处理耗时，将首轮思考限制为三分之一（默认 30 秒），为关闭思考恢复留下约 60 秒。模型目录查询也计入单次时限；保持浏览器 105 秒轮询边界。
- 同一 conversationId / turnId 的前次规划经关闭思考恢复成功时，后续规划沿用 off，申请 1200 输出预算和完整单轮时限。必须匹配所选模型、原思考等级和控制策略版本；新执行轮、用户确认后开始的执行轮、策略变化或前次失败均重新尊重原选择。复用现有有界运行记录，不修改用户默认设置，不持久化为个人偏好。轨迹通过 recoveryFromRequestId 关联来源。
- 重试只运行模型生成，不重新运行整个引擎；保留原始需求和实际 observations。恢复后的结果仍经工具名称、参数、应用范围和已加载工具校验。
- 每次尝试分别消耗每日请求预算，遵守冷却、取消和策略变更。原始思考选择与实际降级分别记录，合计仅累加服务实际返回的 token；超时缺少用量时明确标记为部分已知。
- 返回错误码贯穿 HTTP、扩展消息和步骤错误记录；时间线与完整历史显示尝试详情和真实尝试次数。

## 验证

`test/local-ai-planner-recovery.test.mjs` 覆盖预算、思考空输出、超时、总截止时间、取消、控制策略、请求预算、非法工具、冷/热加载上下文，以及引擎多轮不重放前序动作。`test/local-ai-bridge.test.mjs` 覆盖错误码与尝试元数据穿过扩展消息边界。

真实验证只生成用户原始需求的计划，不执行清空队列、搜索或播放。模型规划成功与真实音乐操作验收分别记录。

本轮结果：267/267 相关回归通过，修改脚本语法检查和 `git diff --check` 通过。

- 原始复合需求、medium、4096 输出预算：真实 Qwen 约 52.7 秒返回 `music.state` + `continue:true`，总输出 1097、其中思考 1077，未触发重试。
- 临时测试进程将输出预算降至 64（未写入用户配置）：首轮返回 63 个思考 token，识别为预算耗尽；第二轮 off 返回合法 `music.state` 计划，总耗时约 5.7 秒。两次用量及失败原因均可追踪。
- 当次 API 核对的已加载实例上下文为 208384、parallel 为 4；截图保存配置显示 40960。以上为运行时快照，不将截图值当作当前实例实测值。
- 真实音乐队列操作和 Chrome 扩展重新加载后的界面验收未执行。

后续发现并修复了独立的 6200 输入预算拦截问题；实际模型上下文预算与完整多轮验证见 [上下文预算修复](assistant-context-budget-20260918.md)。
