# 桌面助手路由、确认与通用回答

日期：2026-10-21。依据 `docs/superpowers/specs/2026-10-21-desktop-assistant-routing-design.md` 分阶段实施。未提交 Git。服务已重启、正式原生组件已构建到原注册路径、Chrome 中“中国风景时钟”已重新加载并保持启用。首轮业务验收使用隔离替身；后续经用户授权完成桌面真实音乐起播与恢复，见本文末尾。未重放提醒或任务写入。

## 阶段一：新目标与旧证据

`music-intent.js` 的闭合语法增加无候选时的“随机播放音乐 / 歌曲 / 歌”。歌手、风格、否定、条件与复合要求仍交给原规划器。命中后使用原来的 Todo → `music.state` → `music.queue.play`，桌面来源先确认，整条路径没有模型调用。

`Contract.routeRequest` 区分新目标、明确引用、搜索词替换和澄清。新的独立目标保留同一会话背景，清除业务 memory、observations、候选与旧计划；明确新会话才清除背景。`goalId` 跟随未完成事项，选择/澄清的新 `turnId` 不会丢失已经完成的 Todo。Context 保存来源 goalId，模型投影增加 currentTurnId / goalId 与 historical / current-goal；服务端白名单校验，旧快照没有来源时不冒认为当前执行观察。历史仍可摘要/回读，不能证明当前播放器状态。显式新会话也不能删除未解决的 unknown 回执；纯问答可以完成，写操作仍被拦截。

非规则路径中，校验后的未完成音乐队列 Todo 若提前 done、尚无本目标队列查询、没有 unknown，且 `music.state` 在当前目录可用，服务仅将本次计划投影为这一条无参只读查询，并记录 `evidenceRecovery=todo-incomplete:music.state`。由原 Engine 执行和计入预算；查询尝试后再次 done 仍以 todo-incomplete 拒绝。补查不会直接播放，不改变 Todo 验收或增加恢复循环。

## 阶段二：桌面写入确认

`assistant-tools.js` 在真实副作用依赖调用前检查来源，包括播放器、队列、视频打开、提醒、任务/工作日志持久化和明确记忆写入。既有 review 卡复用；候选直接点击也须经过确认。桌面来源在同一目标的后续输入中只会保留或收紧，不因转到浏览器续接而丢失。

新确认卡保存任务/版本、10分钟有效期、原步骤/候选，以及实际依赖名称和完整实参的 SHA-256 指纹。确认前做完解析和读取，写入依赖尚未调用。确认后重新走原执行器、重新读取资源，并在真正写入前核对指纹；参数/资源改变则拒绝，不自动采用新值。存储预览显示新记录的实际中文字段，不展示整个存储、凭证或引用内部结构。指纹输入上限4 MiB；卡片不保存闭包或可执行代码。

成功确认回到原步骤/候选的真实回执，继续 Todo。`sideEffectStarted`、unknown、取消、版本、幂等与有界执行继续使用原 Engine。固定键 `quickAssistantMusicIndexV1` 的既有 ≤200项检索索引属于只读查询缓存，不作为业务写入要求确认；不得扩充到任意存储键或授权缓存。

## 阶段三：原生 @ / 动作菜单

Chrome 从 `AssistantContract.apps/skills` 下发6个应用及已登记动作的有界纯文本目录。协议保持当前 v10；`assistantState` 回执新增 `assistantCatalog:1` 能力探测，支持者才接收 `assistantCatalog` 命令。旧组件继续手输。目录 revision 当前为2026102101，修改目录投影时须递增；每连接只发一次，重连重发。原生拒绝回退版本及同版本异文，迟到目录只刷新候选，不改文字。

原生 `AssistantModel` 复用 Foundation 正则和纯数据解析；面板复用 AppKit `NSTextView` 编辑/撤销接口、`NSStackView` 与原确认窗口，无新增依赖、权限、网络或独立任务库。仅前两个前置命令片段触发；名称、ID、别名本地匹配，精确优先、排序稳定。上下键选择，Tab/Enter只补全并保留输入焦点；空匹配不发送，Esc先关菜单。菜单关闭的 Tab/Shift-Tab 保持原焦点导航，IME marked text 不截获。选中应用保留可编辑/可删除的 `@appId ` 前缀，正文不丢失。

“新需求”按钮发送明确布尔 `newConversation`，保留任务/版本绑定和正在运行互斥；原生不自行清任务。状态显示“已指定 / 自动识别 / 继续当前事项 / 通用”。目录与状态异步更新不阻挡编辑。

## 阶段四：通用能力与计算

优先明确应用、有效引用和确定性规则，其余在原有 outline 内选择已登记能力，不增加固定分类模型调用。任务、工作日志增加明确动作的本地范围判断。没有明确应用时，受校验 Todo 只可落到一个应用；跨应用目标要求澄清。

新增独立 `answer` 结果：只用于符合正向语法的纯解释、分析、改写等请求，最多1500字，禁止与工具/完成标记混合；含外部动作、当前资源或实时来源要求时拒绝纯答案替代执行，回答不能声称动作已经执行。Engine 使用已回答终态和原历史/展示/取消链；迟到回答不能覆盖取消。

明确的解释/改写省去不相关工具目录，仍走同一次 Gateway、同一分词/超时/预算；分析与计算保留已有能力目录。纯解释路径也在服务端拒绝附加执行目标。需要资料但没有工具来源时只能说明缺口。

临时工具仅复用既有 `compute.run` 与 QuickJS-WASM 子进程沙箱。生产 `computeEnabled=false` 保持原值；无I/O、资源上限、取消、工具目录隐藏规则均未扩大。没有引入新 SDK 或解释器；继续使用 pi 0.85.1、LM Studio SDK 2.1.0、QuickJS 0.32.0 的既有公开API适配。

## 拼音对齐与真实窗口复查（2026-10-21 后续）

用户截图中的 `@yin` 无结果已复现：原生只做字面包含匹配，浏览器则使用 `AssistantMatch.rank` 与 `PinyinMatch.match`。现由 `assistant-matcher.swift` 使用系统 JavaScriptCore 调用**原样随应用打包**的 `js/assistant-match.js` 和 `vendor/pinyin-match/pinyin-match.js`，没有移植第二套拼音算法。动作使用名称/ID，应用使用名称/现有别名，与浏览器字段和评分顺序一致。

只在初始化时执行两个固定 Bundle 资源，用户输入和目录通过 `JSValue.invokeMethod(...withArguments:)` 作为数据传入，不插入脚本文本；不导出宿主对象、不读取用户脚本、不联网、不执行模型代码，不影响 compute 沙箱。输入≤40个UTF-16单元、候选≤64、序列化参数≤64KiB；仅缓存最后一次匹配，目录或查询变化会失效。缺少/损坏匹配资源时显示组件不可用，不静默换自写匹配器。既有 pinyin-match MIT 依赖使用README记录的 SHA-256 `11fbf02727f6eb90d842a3e9c29eda191b38e293bf01202756e7d7be94867ee7` 锁定，构建校验并带入许可证。

使用公开的 [Apple JSContext](https://developer.apple.com/documentation/javascriptcore/jscontext) 和 [JSValue](https://developer.apple.com/documentation/javascriptcore/jsvalue) API；macOS现有系统框架，无新增npm/Python依赖，无扩展CSP变更。新增Swift源已加入正式构建和原生自测清单。

原生自测使用真实JavaScriptCore与浏览器Node入口逐项对照32个查询，包括 `yin/yinyue/yiny/yy/nz/gzrz/renwu`、中文、别名、动作拼音和标点文本；结果及排序一致。相关JS回归39项通过。正式组件已重新构建，Chrome中已重新加载。

真实窗口复查发现两个独立情况：按 `com.timekeeper.desktop` 定位时，旧 `ConfirmationQA.app` 与正式组件存在相同Bundle ID，工具明确返回歧义；使用正式完整路径后成功读到水母和桌面助手输入框。实际配置的快捷键是 `⌃⇧空格`，不是默认的 `⌃⇧B`。随后实时快捷键面板明确显示“需要先开启桌面水母常驻”，常驻关闭时原生按既有合同注销助手热键、隐藏助手入口；此时不能把窗口探测超时当作模型或规划超时。用户随后明确同意临时开启、验收后恢复关闭，已按此执行并读回关闭状态。旧QA包未删除或改写。
