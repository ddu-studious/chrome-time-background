# AI 工作台：强制 Todo 路线与逐项回执验收

## 问题与证据

2026-09-28 10:56:29（北京时间），本机历史会话 `14a62af4-2edf-4ce7-b6f2-10c477b7a966` 的最后一次规划 `342b8e878621bdff93996af647b5a0a0` 返回 `{"done":true}`。该轮输入仍保留完整四项原文：检查并清空队列、追加许巍热歌、追加法老热歌、随机播放。

真实业务回执只有 `music.state` 和确认后的 `music.queue.clear`；没有两位歌手的搜索、集合读取、追加或播放回执。旧执行器只要求存在成功回执并且最后一条不是失败/unknown，没有逐项目标验收，因此错误显示整个任务完成。截图的“5个动作”含规划和读取记忆等内部操作，不代表完成了五个业务目标。

## 路线与权责

- `js/assistant-todo.js` 是原任务快照内的进度适配层，存于同一个 `quickAssistantTaskV1` 的 `todoTips`。不建立第二个活动任务库，不启动另一套执行循环。
- `Tools.plan` 为新任务创建原始目标和分项来源。模型首次通过独立的 `planningPhase=outline` 返回覆盖所有来源的 `todoTips`（不执行工具）；保存后才进入 `execute` 规划第一步工具；本地确定性计划由原解析器的原子步骤建立 Todo。
- 原文按换行、分号形成不可遗漏的来源。一行内多个目标由模型拆分。最多12项，按来源顺序排列；每项包含展示文字、来源下标、最终工具和固定验收参数。模型不能填写完成状态、资源引用或版本，也不能在后续轮次覆盖清单。
- 每轮规划都收到原始目标、完整清单及当前事项。当前任务和观察仍按原规则输入，不能用 Todo 代替权限、候选选择、真实引用或业务版本。
- Engine 将实际执行日志绑定当前 Todo，只在 `Context.observe` 已保存成功回执后勾选，并引用原回执 ID。等待选择、等待确认、失败、取消和 unknown 均不勾选。
- 对本次队列场景，搜索和集合读取不能完成“追加”；改模式不能完成“随机起播”。清空必须有零首回执，真实 `empty/count=0` 的状态也可满足条件清空；stale/unavailable 不可。随机播放还要求回执 `isPlaying=true` 且模式匹配。
- 模型提前 `done` 进入原有有界恢复。漏写 `continue` 时，只要还有待办仍继续规划，并保持音乐搜索的分步对象引用模式。当前队列事项也校验工具类别和固定参数，阻止提前播放或把清空改为保留。
- 继续执行、确认和选择沿用进度；压缩不改变 Todo；后台中断和取消不接受迟到结果。新需求重新建立清单。需要删除、重排或改变已建路线的验收目标时，应以完整的新需求重新规划，当前不提供模型任意改写清单的接口。仍保留12轮规划、12工具、5分钟、最多3次恢复和相同错误重复停止的边界。
- 工作台通过 `textContent` 展示同一快照的完成数及每项状态，模型没有单独的勾选接口。历史调用在既有正文策略允许时记录清单。

## 2026-09-29 队列播放误判与快捷规划

### 实际原因

本机历史会话在 10:07:46 输入“随机播放队里的歌曲”。旧 `MusicIntent.artistRequest()` 把“随机播放队里”误作歌手名，`Contract.localPlan()` 在队列词检查前返回 `music.intent`。本地计划随后被 Todo 的随机起播完成条件拒绝，产生一次约 70ms 的 `ASSISTANT_PLAN_INVALID`，占用一次错误恢复；该失败没有模型调用或业务写入。后续模型清单和队列起播成功，另有一次 30 秒低思考超时由原关闭思考恢复处理。最后真实回执为 `music.queue.play`、随机模式及 `isPlaying=true`。

### 实现边界

- `MusicIntent.queuePlayRequest()` 只识别完整的播放当前/已有队列短句，返回可选 `shuffle` 模式。歌手解析排除队列词和播放控制词；具名歌手请求保留原处理路径，复合及条件请求交给完整规划。路由将这些明确短句识别为独立音乐需求。2026-09-29：识别语法扩展为封闭语法（新增“列表歌曲”等真实说法），并为裸“随机播放”增加“无待选候选”门控，见 [assistant-speed-20260929.md](assistant-speed-20260929.md)。
- `Tools.plan` 的确定性路径先建立并保存单项 Todo，下一轮只读 `music.state`，仅在本任务最新成功回执为 `ready` 或用户明确播放的 `stale`、曲目数大于零且含真实 `revision` 时提交 `music.queue.play`。`stale` 沿用原受控恢复路径，起播成功后才更新队列状态。Engine 的 Todo、版本、预算、取消、副作用标记、unknown 和重复动作拦截继续生效；完成仍取决于播放回执。空队列与 `unavailable` 状态只提示用户核对。
- 其他本地快捷候选在返回前用现有合同及 Todo 做不执行预检。候选不满足 Todo 时，记录一次“本地快捷规划未命中”的信息轨迹并进入原模型 `outline`；真正的模型或工具失败仍走有界错误恢复。
- 复用本仓库 `MusicIntent`、`AssistantContract`、`AssistantTodo`、Engine 及既有音乐业务 API；本次没有新增依赖或调用上游 pi API。pi 0.85.1 的公开能力与不适用范围沿用本文上游复用核验，本地快捷路线只负责保守识别和计划投影。
