# 快捷助手记忆方案：开源项目对比与接入建议

调研日期：2026-09-17。范围：本仓库快捷助手，优先本地、轻量、中文、可撤销、可替换的实现。

**结论：先建立结构化个人偏好和实体记忆，以 SQLite 为事实存储；需要语义召回时增加 sqlite-vec。Mem0 OSS 是首选现成记忆引擎对照组，Mastra Memory 是愿意扩大框架改造时的候选。** 不建议为当前音乐助手直接迁入完整智能体平台或知识图谱系统。

这是一份基于当前源码、官方 GitHub 仓库及文档的选型评估，不是安装后的性能排行榜。本轮未安装依赖、下载模型、修改运行配置或接入真实个人数据。轻重与适配度是架构判断；没有实际测得的 RSS、延迟、中文准确率。公开基准不等于本机效果，公开仓库也不等于所有宣传能力都能离线使用。

**一、先确认我们需要的“记忆”**

| 记忆种类 | 本项目例子 | 保存与使用原则 |
|---|---|---|
| 会话状态 | 刚选中的歌手、“他的热门歌”中的“他” | 随会话管理，有有效期；不提升成永久偏好 |
| 明确个人偏好 | 音乐场景说“某歌手的热门歌曲”通常表示想播放 | 有明确来源和适用场景；本次指令优先 |
| 实体与别名 | 用户确认的“张杰”对应哪个平台的歌手 ID | 名称、别名、平台、真实 ID 分开；执行前检查当前可用性 |
| 事件与经历 | 上次播放了哪组歌曲、用户纠正过什么 | 带时间、来源、结果；失败与成功分开 |
| 行为推测 | 多次跳过现场版 | 先作为弱排序信号，不能一次行为就生成永久禁令 |
| 操作经验 | 点歌时先识别歌手再取热门曲目 | 优先写入可测试的业务流程；不让记忆私自改变权限 |
| 知识资料 | 歌手介绍、书签、文档 | 可用 RAG 检索，但不与用户偏好混为一类 |

“记住你喜欢谁”和“知道怎样完成播放”是两个问题。即使接上最强记忆引擎，若解析协议仍把目标丢掉、执行器仍无条件等待候选选择，原问题依旧存在。

**二、当前仓库的基础和缺口**

以下是本轮源码核验，不代表运行中的配置值或真实播放验收：

| 已有能力 | 位置 | 对选型的影响 |
|---|---|---|
| 自有 Node.js 本机服务，无声明的第三方运行依赖 | `local-ai/package.json` | 能在现有进程增加小组件；引入 Python/Docker 都是新增维护面 |
| 候选、草稿、观察和工具引用 | `js/assistant-engine.js`、`js/assistant-tools.js` | 是任务上下文，不能直接当跨会话个人画像 |
| 历史文件与留存设置 | `local-ai/history-store.mjs`、`local-ai/server.mjs` | 使用 `history.json`，源码默认不留存正文、保留 30 天；不能假设已有完整聊天语料 |
| 本地生成及 embedding 接口 | `local-ai/provider.mjs`、`local-ai/embedding-service.mjs` | 可复用模型入口；新记忆引擎仍需适配 |
| 简单需求走本地规则 | `js/assistant-tools.js:70`、`local-ai/assistant-service.mjs:26` | **仅把记忆塞入模型提示词会漏掉本地规则路径** |
| 模型输入约 6200 tokens 的估算预算 | `local-ai/assistant-service.mjs:59` | 需要精简召回，不适合每次附上全部历史 |
| embedding 与生成共享 busy 限制 | `local-ai/provider.mjs:29`、`:42` | 后台记忆抽取若不经统一调度，会抢占前台请求或收到繁忙错误 |
| 另一个进程使用 better-sqlite3 | `cursor-bridge/src/services/database.ts` | 说明仓库已有经验，不代表主助手已经共享该数据库；不应直接耦合旧进程 |

建议由本机 AI 服务拥有独立 `memory.db`；浏览器扩展只持有必要的偏好快照和版本。明确偏好先按键查找，语义检索只补充相关经历。旧历史文件不在本轮迁移。

**三、十二个 GitHub 项目的横向比较**

“轻量”综合考虑新增进程、依赖、模型调用和对现有代码的改造；不是官方实测数值。许可证为本轮可见主仓库/文档标识，具体发行版和子目录仍需按锁定版本核对。

| 项目 | 类型及本地形态 | 优点 | 本项目的主要代价 | 建议 |
|---|---|---|---|---|
| [sqlite-vec](https://github.com/asg017/sqlite-vec) | SQLite 向量扩展，C；Node 可加载；MIT/Apache-2.0 | 无独立数据库服务，能与结构化偏好放在同一文件 | 不负责抽取、冲突、遗忘策略；pre-v1 需锁版本 | **第一阶段优先组件，语义检索按需加** |
| [LanceDB](https://github.com/lancedb/lancedb) | 嵌入式检索库，Python/TS；Apache-2.0 | 向量、全文、多模态检索，后续知识库扩展空间大 | 用户偏好治理仍要自己做；对少量偏好有额外复杂度 | 文档/书签规模扩大后的存储备选 |
| [MCP Memory Server](https://github.com/modelcontextprotocol/servers/tree/main/src/memory) | TS 参考服务器，实体/关系/观察的文件持久化；仓库 MIT | 小、可读，适合多客户端共享与原型 | 默认节点搜索是文本包含匹配；自动学习策略仍由调用方负责；现有助手需加 MCP 适配 | 借鉴数据结构，不作为首选语义引擎 |
| [Mem0 OSS](https://github.com/mem0ai/mem0) | 独立记忆库或服务，Python/TS；Apache-2.0 | 抽取、检索和管理接口齐全，可换 LLM/向量后端 | 默认不等于全本地；TS 默认向量存储在内存；模型调用、持久化和业务冲突需配置 | **首选现成引擎对照组** |
| [Memobase](https://github.com/memodb-io/memobase) | 用户画像/事件服务；FastAPI + PostgreSQL + Redis；Apache-2.0 | 面向“了解用户”，画像结构可控，有批处理 | 对单人桌面工具运维偏重；本轮可见 main 最近提交较旧 | 学习画像设计，暂不直接引入 |
| [LangMem](https://github.com/langchain-ai/langmem) | Python 记忆工具库；MIT | 有抽取、整合和后台更新原语，可接不同存储 | 当前 JS 执行链需跨语言适配；示例 InMemoryStore 不耐重启 | 若未来采用 LangGraph 再优先考虑 |
| [Mastra Memory](https://github.com/mastra-ai/mastra) | TS 框架记忆组件，可用本地 LibSQL | 用户级 working memory、历史召回和观察式记忆；同语言 | 最顺畅接入依赖 Mastra Agent 生命周期；不能视为零改造插件 | **第三候选，框架扩展路线** |
| [Hindsight](https://github.com/vectorize-io/hindsight) | retain/recall/reflect 服务，PostgreSQL/pgvector，可嵌入式启动；MIT | 面向事件、经验与反思，提供 Node 客户端，文档列出本地模型及 Apple Silicon 支持 | 嵌入式不等于 SQLite 小库，仍有数据库和后台处理负担 | 复杂经历记忆阶段再评估 |
| [Graphiti](https://github.com/getzep/graphiti) | Python 时序知识图谱；Neo4j/FalkorDB 等；Apache-2.0 | 适合关系、时间变化和旧事实失效 | 抽取和图数据库增加成本；官方提示小模型结构化输出风险 | 当前点歌偏好无需图谱；关系推理需求明确后再引入 |
| [Cognee](https://github.com/topoteretes/cognee) | Python 知识图谱记忆平台；Apache-2.0 | 适合把资料、决策、会话组织成关联知识 | 数据加工和索引流程多；本地模型需额外配置 | 统一知识库路线候选 |
| [OpenViking](https://github.com/volcengine/OpenViking) | 文件系统式上下文数据库，分层加载、会话提炼 | 把资源、用户记忆和经验统一组织，便于检查来源 | 范围大于偏好库；摘要/抽取仍消耗模型；当前 main LICENSE 为 AGPL-3.0 | 关注整体设计，第一阶段不引入 |
| [Letta Code](https://github.com/letta-ai/letta-code) | 有状态 Agent runtime；Apache-2.0 | 记忆块、技能学习和长期身份与执行循环结合 | 对现有受控工具执行器属于较大架构替换 | 想重建通用 Agent 平台时再选 |

补充一个不依赖新框架的基线：版本化 JSON/Markdown 偏好文件。适合很少且明确的偏好，易检查、可导出；并发修改、结构化查询、来源级删除和规模扩大后不如数据库。可作为最小验证或导出格式，而非不断膨胀的全量提示词。

**四、几个会改变选型结论的事实**

1. **Mem0 的 TS 开源库不是仅有云 API 包装。** 官方入口是 `mem0ai/oss`，但 quickstart 默认使用 OpenAI 生成/embedding、内存向量库和 SQLite 历史。因此“装了 npm 包”既不代表离线，也不代表重启后召回仍然存在。Python 的默认本地 Qdrant 和 TS 的默认内存库不可混说。[Node 官方说明](https://docs.mem0.ai/open-source/node-quickstart)、[Python 官方说明](https://docs.mem0.ai/open-source/python-quickstart)。
2. **Mem0 宣传成绩不能直接当本地 OSS 成绩。** 官方评估页明确区分包含专有优化的托管平台。采用它的理由应是少写记忆流程，而不是未经验证地承诺相同准确率。[官方评估说明](https://docs.mem0.ai/core-concepts/memory-evaluation)。
3. **Memobase 产品定位贴近，但维护节奏要谨慎。** 本轮可访问的 main 提交页顶部为 2026-01-11，SHA 前缀 `358c16b`；README 推介 Acontext。这不能证明项目废弃，但不足以把它视为与频繁发布项目相同的维护风险。[提交记录](https://github.com/memodb-io/memobase/commits/main/)。
4. **Memori 与 Mem0 是不同项目。** [Memori 当前 README](https://github.com/MemoriLabs/Memori) 的快速开始需要 Memori API key，Advanced Augmentation 也涉及其服务。即使支持自带数据库，也不能据此断言整个抽取流程完全本地。由于离线核心路径本轮未核实，不把它放入上面十二项主候选；不会按旧文章中的“轻量 SQL 本地记忆”直接推荐。
5. **Letta 的活跃代码位置已经变化。** 原 [letta 仓库](https://github.com/letta-ai/letta) 指向 `letta-code`，旧 V1 API server 在 archive 分支。不能继续按旧 Python 服务教程估计当前接入成本。
6. **sqlite-vec 应锁稳定版本。** [发布列表](https://github.com/asg017/sqlite-vec/releases)可见 v0.1.9 及 v0.1.10 alpha；当前需求不需要为了 ANN 新能力使用 alpha。优先验证基本写入、删除、筛选、备份恢复和目标 Node/arm64 的加载能力。[Node 集成文档](https://alexgarcia.xyz/sqlite-vec/js.html)。
7. **Mastra 的模型默认值要覆盖。** 观察式记忆支持本地 LibSQL，但启用 `observationalMemory: true` 的文档默认观察模型为云端模型。它也需要自行配置模型和存储；核心 Apache-2.0，`ee/` 另有企业许可证。[观察式记忆](https://mastra.ai/docs/memory/observational-memory)、[许可证说明](https://github.com/mastra-ai/mastra#licensing)。
8. **Graphiti 不应按过时轻量部署指南选 Kuzu。** 当前 README 已将 Kuzu 标记为弃用，另提供 FalkorDB Lite 路线；即使嵌入式部署，时序图谱抽取的模型成本仍然存在。[当前安装说明](https://github.com/getzep/graphiti#installation)。

维护信号上，本轮 [Mem0 发布页](https://github.com/mem0ai/mem0/releases)可见 9 月发布，Node SDK v3.1.8 与 Python SDK v2.0.20；[Mastra 发布页](https://github.com/mastra-ai/mastra/releases)有持续多包变更。活跃意味着有人维护，也意味着升级成本；本报告不以 star 数代替质量，不宣称做过全部 issue/依赖的审计。

**五、真正适合本项目的三条路线**

| 比较项 | A：SQLite + 自有策略 + 可选 sqlite-vec | B：Mem0 OSS | C：Mastra Memory |
|---|---|---|---|
| 主用途 | 准确执行明确偏好，必要时找相关经历 | 借用完整记忆抽取和检索流程 | 将记忆与 TS Agent 生命周期整合 |
| 新增基础设施 | 可留在当前 Node 进程 | TS 库可同进程，持久化后端须明确；Python 服务则新增进程 | 可同 Node，LibSQL 本地文件；引入框架依赖 |
| 中文 | 自己确保短词、实体、否定和范围 | 抽取模型、embedding、关键词管线都要实测 | working memory 模板与观察模型都要实测 |
| 确定性偏好 | 按键查找，容易稳定生效 | 外围保留结构化偏好表更稳妥 | 结构化 schema/模板需映射到业务策略 |
| 更新、删除、失效 | 自己维护，有最大控制权 | 有现成 API，但业务覆盖规则仍由我们决定 | 有框架生命周期，跨数据层删除仍需验证 |
| 接入现有规则路径 | 容易：执行前统一取偏好 | 仍须加适配，不能只接模型 | 需桥接或改造现有执行循环 |
| 主要成本 | 自己实现一小层策略与管理界面 | 默认值、后端差异、抽取质量和额外调用 | 生命周期迁移、后台模型调用、框架升级 |
| 我的排序 | **第一** | **第二，直接对照验证** | **第三，有框架升级意图时再投入** |

A 不是重新实现一个通用 Mem0。第一版只做偏好、实体、来源和事件的窄模型，不做自动知识图谱、递归反思或任意文本自我改写。它适合当前明确的音乐/提醒/视频场景；若未来长期经历问答成为核心能力，自研范围会扩大，B 的价值随之增加。

也不建议第一天把 SQLite、LanceDB、Mem0、图数据库全部叠加。选一个事实主库，一个可替换召回接口，避免多个系统分别认为自己掌握“最新偏好”。

**六、建议的记忆流程与数据边界**

```text
用户输入 + 当前应用 + 本次明确约束
                ↓
读取结构化偏好 / 已确认实体（不调用大模型）
                ↓
必要时检索少量相关经历（全文 + 可选向量）
                ↓
统一构造 effectiveContext
          ↙                     ↘
    本地规则规划                模型规划
          ↘                     ↙
         校验、执行、读取真实回执
                ↓
           先给用户结果
                ↓
可选后台抽取 → 校验来源/范围/冲突 → 保存或形成候选记忆
```

明确“记住……”的操作要先持久化再回复已保存；普通任务的自动总结放后台，不能阻塞播放。抽取也必须通过现有本地 AI 调度入口，遵守忙碌、超时、取消和预算控制，不能让某个 SDK 绕开网关直接与前台争用模型。

建议最小表结构：`memory_preferences`、`memory_entities`、`memory_events`、`memory_sources`；有需要再增加 `memory_embeddings`。字段至少包含：用户/应用范围、键或实体 ID、值、来源事件、明确陈述或行为推测、有效时间、版本、被哪条记录替代。不要只存一段无法管理的“用户总结”。

优先级：本次明确指令 > 当前适用的明确偏好 > 经确认的长期事实 > 行为推测。权限边界独立于这个优先级，不由记忆扩大。

冲突不能只看更新时间。例如“今天想听现场版”是当次例外，不应覆盖“不特别说明时优先录音室版”。“以后都先展示，不要自动播放”才是长期策略更新。新模型抽出的结论不能覆盖用户明确设置，置信度只作内部排序，不能当经过校准的正确概率。

以当前音乐需求为例，可保存以下两条彼此独立的信息：

| 记录 | 例子 | 不应推导的结论 |
|---|---|---|
| 意图习惯 | 音乐场景，省略动词的“某歌手热门歌曲”默认按播放目标处理 | 用户明确说“搜索看看”也自动播放 |
| 实体偏好 | 用户选择并确认过的平台歌手真实 ID | 仅凭姓名相似就把 AJ张杰 等其他候选合并 |

“播放”与“替换当前队列”仍需分别建模。记忆可以提供用户已设置的队列策略；没有这个偏好时，沿产品既定规则处理，不把本次口头说明擅自扩展成永久清队列授权。

记忆管理界面至少提供：查看、修改、删除、暂停自动学习、导出；展示“来源于哪次明确说明”或“由哪些行为推测”。不要求每一条低风险偏好都弹窗，保存后给轻量提示和撤销即可。临时会话的内容不送入长期抽取。

历史留存与记忆留存是两个设置，但应一起解释清楚。推荐删除一段会话时默认清理仅由该会话衍生的记忆和向量；另有独立证据支持的事实保留并移除已删来源。用户单独保存的设置可保留，但 UI 要说明。彻底删除必须覆盖缓存、向量、待处理任务，防止后台任务把记忆重新写回。

**七、中文、资源和离线边界**

中文不能靠“支持 UTF-8”判断。需同时评估中文事实抽取、短词精确检索、语义召回、否定/时间/例外理解。

SQLite FTS5 的 trigram 全文查询不匹配少于三个 Unicode 字符的子串。“张杰”“周深”因此要走姓名/别名精确索引；复杂文本再用合适分词和语义召回。拼音保留原文、归一化别名，不能把不同歌手的相似拼音直接视为同一实体。[SQLite 官方说明](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。

语义 embedding 可对照两类官方模型卡：偏中文短文本的 [BGE-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)，以及多语言、0.6B、最高 1024 维的 [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)。它们是候选，不代表已在当前 LM Studio 中验证可加载。先用已有 embedding 做基线，仅在中文召回不足时换模型；不要因为采用记忆就立即常驻另一个大模型。

当前 provider 对 Nomic 有 query/document 前缀处理。换 embedding 时需按模型要求调整输入，并保留模型、维度、归一化和模板版本组成的独立索引空间；新索引完成后再切换，不能混查不同空间。

资源估算仅说明量级：一万条 768 维 float32 向量原始数据约 29.3 MiB；十万条约 293 MiB。这不含文本、索引、数据库、进程和模型。真正可能拖慢桌面的通常是抽取/总结、embedding 模型加载、重排和常驻服务，而非几百条偏好本身。对于少量明确偏好，零 embedding 也能完成主要功能。

建议以三种负载实测：无用户请求的空闲、前台点歌、后台批量整理。测前台额外延迟 p50/p95、CPU/RSS、磁盘、生成/embedding 调用次数及失败率，分开报告冷启动和热启动。模型权重与缓存目录初始化可能需联网；离线验收应在初始化后检查断网行为、遥测、后台网络请求，不能只检查 LLM 地址是 localhost。

**八、实际接入范围与分阶段验收**

第一阶段先交付明确偏好和完整音乐目标：

1. 修正音乐意图合同，保留目标动作、对象类型、热门歌曲范围以及本次限制；界面“搜索音乐”提示不机械覆盖显式播放句子。
2. 增加独立 MemoryService，提供读取偏好、保存明确偏好、记住实体选择、删除/导出接口；先用结构化存储完成跨重启记忆。
3. `js/assistant-tools.js` 的规则与模型两条路径共享经过版本校验的上下文；服务端合同显式接收允许的字段。
4. `local-ai/assistant-service.mjs` 按预算注入相关记忆；本地规则直接消费结构化设置。
5. `js/assistant-engine.js` 在任务回执之后记录结果；执行轨迹显示本次用了哪些记忆及来源。
6. 先把“张杰的热门歌曲”闭环跑通，包括同名消歧、只搜索不播放、播放失败、队列策略和撤销。

第二阶段比较 A 与 B：同一模型、同一 embedding、相同语料、相同输入预算和本地网络策略，对比 SQLite 路线和 Mem0 OSS。先在合成或用户选定的样例上测试，不批量读取所有历史。B 通过测试前只做影子召回，不直接影响播放。Mastra 若进入比较，要单独计入执行生命周期迁移成本。

第三阶段才增加行为学习和事件召回：把反复选择/纠正转成可解释的弱偏好；按来源、时间、明确程度整合；加入 sqlite-vec 或替换召回后端。只有出现真正的关系/时间链推理需求，才重新评估 Hindsight/Graphiti；资料知识库成为重点时再比较 LanceDB/Cognee/OpenViking。

| 类别 | 样例 | 预期 |

**九、决策建议**

选择 A，是因为我们已经有受控执行器和本机模型入口，当前痛点集中在明确偏好、歌手身份与目标丢失，适合小范围补齐。

保留 B，是为了验证现成抽取/召回是否能在相同资源预算下明显减少维护量、提高中文经历记忆质量。一旦对照结果更好，通过 MemoryService 适配替换后端，无需重做前端或播放器。

选择 C 的前提是同时希望采用 Mastra 的 Agent/工作流体系；仅为了记住点歌习惯，框架迁移收益目前不明确。

后续实施前需要验证的未知项已明确：目标 Node 的 SQLite 扩展加载、所选 Mem0 TS 版本的持久化后端、LM Studio 接口适配、中文评测、后台任务与现有忙碌锁的兼容，以及真实播放器的恢复行为。这些不会通过项目 star 数或官方英文基准自动得到答案。
