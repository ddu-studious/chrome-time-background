# 快捷助手会话与执行过程 v1

## 1. 目标

让用户在快捷助手内同时获得三件事：

1. 看见本轮正在做什么、用了哪些工具、是否真的完成。
2. 完成后不被过程信息打扰，但可以随时展开复盘。
3. 下一次输入仍属于当前会话，可以直接引用上一轮候选、对象和结果。

本设计中的“全部动作”指程序可观察的规划摘要、模型调用、工具、内部操作、接口请求、状态和回执，不展示模型内部思维链。

## 2. 核心体验

### 2.1 运行中

- 保留当前顶部命令输入区，下面扩展为“本次对话 + 执行过程”双栏。
- 左栏负责用户意图、助手回复、候选结果和最终业务结果。
- 右栏按时间显示动作，默认使用业务语言，例如“搜索歌手”“读取热门歌曲”“开始播放”。
- 每个动作显示状态、耗时和工具标签；展开后才显示脱敏后的参数、结果和错误。
- 当前动作使用紫色脉冲，成功为绿色，等待为灰色，错误为红色。
- 用户可停止本轮；已成功的外部动作不能伪装成回滚成功。

### 2.2 本轮完成

- 成功结果稳定展示后，将右栏收成一条执行回执：`已完成 · 5 个步骤 · 2.4 秒 · 展开过程`。
- 自动收起只发生在成功状态；失败、等待确认和需要补充信息时保持展开。
- 收起不会清空本次会话、候选集合或工具记录。
- 点击“展开过程”恢复同一条时间线和展开状态。

### 2.3 继续对话

- 底部输入框始终属于当前会话，提示语可根据场景变化，例如“继续说，例如：播放第 2 个”。
- `Esc 收起`只隐藏面板，不结束会话。
- `新需求`才显式结束当前会话并创建新会话；需要二次确认仅限存在未完成操作时。
- 页面重开后恢复最近一个未显式结束的会话，但不会自动重放中断动作。

## 3. “播放第几个”的确定性处理

以“张杰”为例：

1. 第一轮搜索产生一个有稳定顺序和稳定 ID 的 `candidateSet`。
2. 用户输入“播放第 2 个”时，先由本地序号解析器读取当前会话最后一个可见候选集合。
3. 序号有效且候选仍在有效期内时，直接把候选 ID 交给播放工具，不再搜索，也不需要模型重新猜测。
4. 执行过程显示“解析上轮候选 → 播放候选 2 → 播放器确认”。
5. 序号越界、存在多个同等相关候选集合或候选已失效时，才要求澄清或重新查询。

建议保留以下会话内存：

```js
conversation.memory = {
  activeScope: 'music',
  lastIntent: 'music.search',
  candidateSet: {
    id: 'candidate-set-id',
    type: 'artist',
    createdAt: 0,
    expiresAt: 0,
    items: [{ index: 1, id: 'artist-id', title: '张杰', subtitle: '内地男歌手' }]
  },
  selectedEntity: null,
  playback: null
};
```

候选展示顺序一旦交给用户，本次会话内不能静默重排。工具执行前仍需按现有规则校验候选是否过期、播放器状态是否变化。

## 4. 状态模型

当前的任务状态需要拆成“会话”和“轮次”两层，避免一轮完成后丢失上下文。

```text
Conversation
├── id / createdAt / updatedAt
├── state: open | closed
├── turns[]
├── memory
└── activeTurnId

Turn
├── id / conversationId
├── status: planning | running | waiting | completed | failed | cancelled | interrupted
├── input / reply / result
└── trace[]
```

- 每次输入创建新 `turnId`，但在用户点击“新需求”前保持同一 `conversationId`。
- `completed`只结束当前 Turn，不关闭 Conversation。
- `failed`后允许继续追问或重试，并保留已经确认成功的动作。
- 恢复到中断会话时，状态显示 `interrupted`，不得自动重复有副作用的工具。

## 5. 执行过程的信息层级

### 默认层

- 业务标题：搜索歌手、读取热门歌曲、开始播放。
- 状态：运行中、成功、等待、失败、已取消、中断。
- 耗时、步骤编号和父子关系。
- 一句话结果：`找到 12 位同名歌手`、`播放器已确认开始播放`。

### 展开层

- 工具标识，例如 `music.search`、`music.artist.tracks`、`music.play`。
- 脱敏且有界的输入、输出、错误码和错误摘要。
- 模型、思考等级、调用耗时和 token 用量（提供者未返回时明确说明）。
- 子步骤，例如搜索备用接口、准备可播放资源、提交播放、播放器确认、队列保存。

### 不展示

- 系统提示词、内部思维链、凭证、Cookie、Authorization、真实播放链接、原始音频。
- 没有实际回执时，不使用“已播放”“已保存”等成功措辞。

## 6. 前后端建设建议

### 6.1 统一事件源

继续以现有 `ctx.trace` 为唯一动作入口。一次 trace 同时输出到：

1. 当前快捷助手快照，供前端实时渲染。
2. 本机历史存储，供设置页长期回看和导出。

不要让前端分别拼接业务日志和历史接口，否则实时状态与最终记录容易不一致。

### 6.2 快照增量

快捷助手快照增加：

```js
{
  conversation: { id, state, memorySummary },
  turn: { id, status, input, reply, startedAt, endedAt },
  trace: [{ id, parentId, kind, tool, title, status, startedAt, endedAt, elapsedMs, summary }],
  traceRevision: 12
}
```

正文留存关闭时，实时界面仍可展示本轮必要信息；写入历史时继续遵守现有正文开关和脱敏规则。

### 6.3 会话延续

- 提交新输入时，只要 Conversation 为 `open`，就继承 turns、candidateSet、已选对象和业务 observations。
- 上下文仍需有界；发送给模型的最近轮次可以裁剪，但确定性引用对象不能仅依赖被裁剪的自然语言。
- 历史记录只用于回看，不应自动把所有历史会话注入模型。
- 跨会话的长期个人偏好不是本 v1 的默认范围，需要独立授权、可查看和可删除。

## 7. 响应式与可用性

- 宽屏双栏，右栏建议占 38%–42%。
- 窄屏改为单栏：对话在上，执行过程为可折叠抽屉；任何参数都必须换行，不能产生横向滚动。
- 时间线使用真实按钮和 `aria-expanded`；状态不能只靠颜色表达。
- 动效遵守 `prefers-reduced-motion`。
- 新步骤到达时仅在用户位于底部才自动滚动；用户正在查看旧步骤时不抢滚动位置。

## 8. 验收场景

1. 输入“张杰，直接播放”，界面实时出现理解、搜索、匹配、读取歌曲、播放和播放器确认；最终只在收到确认后显示成功。
2. 第一轮返回多个候选后输入“播放第 2 个”，沿用同一 `conversationId`、创建新 `turnId`，不再次搜索，直接播放候选 2。
3. 完成后执行区自动收成回执；手动展开后步骤、耗时、父子关系和详情完整保留。
4. `Esc`隐藏后重新打开，仍能继续当前会话；点击“新需求”后旧候选不可再被“第 2 个”引用。
5. 候选过期、越界或上下文不唯一时，不猜测，明确要求重新选择。
6. 失败、取消、服务重启和迟到成功都保持正确终态；取消不能被迟到结果覆盖为成功。
7. 正文留存关闭时不落盘参数正文；凭证和播放链接始终不展示、不导出。
8. 480px 宽度无横向溢出，键盘可展开和收起每个步骤。
