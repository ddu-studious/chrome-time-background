# 快捷助手：按需工具与逐步决策 v1

日期：2026-09-16。

后续P1已实现，见 [提醒管理、音乐编辑与视频检索](assistant-management-p1.md)。本页保留P0阶段合同和验收记录。

## 本期实现

新增六个音乐工具：`music.state`、`music.queue.list`、`music.playback.setMode`、`music.queue.play`、`music.collection.get`、`music.queue.apply`。新增 `tools.load` 作为工具组发现入口。`music.queue.play` 可传 `mode`，在一次业务调用内设置模式并确认开始播放，避免把“设置模式”误当成“已经播放”。已有音乐搜索、定时、视频与闹钟工具保留。

状态查询基于 Offscreen 播放回执、后台队列和持久化队列，返回 `ready/empty/stale/unavailable`。读取异常不当作空队列。超过300首或格式异常的队列可报告状态，不能截断后写回。只读查询不会更改队列。

队列应用区分 `append/replace` 和 `startPlayback`，因此“追加但不播放”与“替换并播放”有独立合同。仅替换且不播放时，如会移除正在使用的当前歌曲，要求明确后续操作，避免界面队列与声音身份分离。

搜索结果仍由用户选择。逐步任务选择集合后，执行器将真实 `selectedRef` 交给规划器，后续可以读取曲目、追加或播放；无需再由用户判断是否存在队列。普通搜索及原有按钮语义保持兼容。

## 按需加载

- 显式 `@应用` 限定工具作用域；音乐请求不再混入视频工具。未指定应用且语义不确定时保留四个应用的少量基础入口，允许模型路由。
- 音乐基础目录包含搜索、单动作意图、定时、状态和工具发现入口；高级工具分为 `music.playback` 与 `music.queue` 两组。
- 模型只看到已加载工具的完整参数目录，其余只有分组名和一句用途。需要时调用 `tools.load`，下一轮才注入该组工具。
- 对明确的随机/循环/顺序播放请求预加载播放组；用户选中集合后预加载队列组。高置信度预加载减少一次模型往返，长尾能力仍走发现机制。
- 服务端校验模型不得调用未加载工具；发现工具不能越过用户明确指定的应用范围。新能力继续通过统一控制面，不直接访问模型。
- 状态、队列、集合数据先在本地形成受限结构，只将必要摘要、版本与引用送入模型；不发送播放签名 URL、账号凭据或完整300首曲目。

当前音乐首次通常提供5个工具；明确播放模式需求提供7个；两个高级组均需要时最多10个。工具目录随需求扩展，不意味着每次全量注入。

## 决策协议与资源预算

兼容原有最多三步的线性计划。新增协议：

```json
{"steps":[{"tool":"music.state","args":{}}],"continue":true}
```

`continue:true` 每轮只接受一个工具，回执持久化后重新规划；完成后模型返回 `{"done":true}`。缺少对象时可追问；搜索选择、闹钟确认仍作为暂停点。最终成功文案来自实际工具回执，模型不能自行编写成功结果。

每任务最多12轮规划、12次工具调用；保留5分钟执行时限，用户选择后的执行重新计时。历史观察最多6条、12000字符；构造模型输入时最多8条会话，列表预览最多5条，超预算先裁剪旧会话和旧观察。

模型输入使用保守估算预算6200 tokens（中文按每字最多约2 tokens、ASCII按每2字符约1 token估算，并非模型 tokenizer 的精确计数），场景请求输出上限1200 tokens。统一网关取场景请求和控制策略中更小的输出预算；无法压缩到预算内则明确失败，不无限增长上下文。

规划响应中的 `toolContext` 提供本轮工具数、已加载组、估算输入 tokens 和观察数，用于验证加载效果。

## 一致性与恢复

- 写入要求最近状态的 `expectedRevision`；版本由队列身份、当前曲目、播放模式和手动操作版本等生成摘要。
- 播放 URL 准备完成后再次校验状态，避免准备期间的用户操作被旧请求覆盖。
- 资源引用绑定任务、有效期与真实工具结果。集合应用要求已经由用户选择，成功后标记已消费，拒绝同一引用重复应用。
- 同一播放模式策略供工作台和后台使用；后台自然结束支持单曲循环，手动下一首仍切到下一项；随机使用一轮不重复的顺序，FM 保持独立续播逻辑。
- 后台重启不会自动重放未完成操作；用户取消后迟到计划/回执不能引起后续调用。
